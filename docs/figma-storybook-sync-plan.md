# План связи Figma → локальный Storybook

Дата: 6 октября 2026. Статус: план; реализация не начата.

## Цель и согласованные границы

После серии правок пользователь запускает «Сравнить с Figma». Storybook показывает маркер возле компонента и общий список текущих различий. После переноса компонент получает статус «Готово к визуальной приёмке». Маркер снимается только после пользовательского OK.

Схема из исходного чата: машинный реестр → локальный Figma-плагин → существующий bridge → локальный Storybook. «Nudge Bridge» трактуется как роль существующего мостa, а не отдельный установленный продукт.

Первая версия: ручное сравнение, текущая разница, локальное хранение. Автоматическое наблюдение, опубликованный Storybook, совместная работа, синхронизация статусов между компьютерами и полное восстановление после сбоев отложены. Простая защита от устаревшего OK обязательна уже сейчас.

- Storybook: `D:/Codex/figma to storybook`, установлен Storybook 10.6.1, React/Vite. Есть `.storybook/main.ts`, `preview.tsx`; собственного manager/addon пока нет.
- `src/bridge/session.ts`: WebSocket на `127.0.0.1:3846`, pairing и ограничение Origin. Подключения получают временные UUID, доступны имя файла и видимость. UUID и имя недостаточны для постоянного реестра.
- `src/bridge/host.ts`: запуск, остановка, повторное занятие порта и `pinCurrentFile()` уже реализованы. Новый сервис должен следовать тому же жизненному циклу.
- `src/bridge/mcp.ts`: уже есть чтение дерева, preview, SVG и переменных; схема дерева содержит provenance, свойства компонентов, темы и предупреждения полноты.
- В текущем коде не обнаружены HTTP API для Storybook и обработчики `documentchange`/`stylechange`.
- В Storybook есть текстовый реестр, исходные экспорты, последующие обновления, генераторы токенов и контракты. Нельзя объявлять первый экспорт актуальной базой.
- Есть согласованные отличия: derived light-элементы, исключённые варианты, нормализация высоты и поведение, заданное пользователем. Сравнение без этих правил даст постоянные ложные тревоги.

## Главная поправка к модели

Storybook показывает код, но автоматически восстановить из React исходную модель Figma нельзя. База сравнения — снимок, явно связанный с текущей реализацией и её контрактом.

Нужны три отдельные ссылки:

1. `observedSnapshot`: последняя полная прочитанная Figma.
2. `implementedSnapshot`: снимок, для которого завершён перенос в текущий код.
3. `acceptedSnapshot`: снимок реализованной версии, которую пользователь принял визуально.

Экспорт обновляет только `observedSnapshot`. Перенос обновляет `implementedSnapshot`. OK обновляет `acceptedSnapshot`. Ни экспорт, ни техническая проверка не означают визуальную приёмку.

Текущая разница считается между `observedSnapshot` и `implementedSnapshot`. Если разницы уже нет, но реализация ещё не принята, маркер остаётся с пометкой «Ожидает OK». Если Figma изменилась вновь, статус «Требуется перенос» получает приоритет. Отменённая правка убирает соответствующее расхождение; прежний статус приёмки сохраняется.

## Предлагаемая архитектура

`Storybook manager → локальный HTTP API bridge → закреплённая Figma-сессия → существующие методы чтения → нормализация/diff → проектное хранилище → manager`

Bridge владеет чтением и вычислением различий. Storybook addon отвечает за интерфейс. Кнопка сравнения отправляет один запрос; ответ содержит результат и идентификатор отчёта. В первой версии достаточно обычного HTTP и обновления после действий, без SSE/WebSocket для браузера.

HTTP-сервис работает внутри процесса, уже владеющего bridge; новый процесс ради Storybook не запускает второй Figma WebSocket. Отдельный loopback-порт настраивается, конкретное значение выбрать после проверки занятых портов. При конфликте вернуть понятный статус; не оставлять addon подключённым к чужому процессу.

В браузер не передавать Figma pairing code и общий интерфейс `plugin.call`. Для Storybook — отдельная локальная сессия с ограниченными командами, точный allowlist Origin, проверка авторизации и привязка к настроенному проекту. Путь проекта не принимать произвольно из браузера. Для localhost/127.0.0.1 проверить фактический Origin; не разрешать `*`.

Предварительный API:

- `GET /sync/status`: доступность bridge, нужного файла, версия протокола, актуальность последнего сравнения.
- `GET /sync/components`: реестр, текущие статусы и различия.
- `POST /sync/compare`: выбранные `componentIds`, ручное чтение и новый отчёт.
- `POST /sync/implemented`: точный `snapshotId` и идентификатор версии реализации; доступ через CLI/MCP после переноса, не через кнопку экспорта.
- `POST /sync/accept`: компонент, `snapshotId`, идентификатор проверенной реализации и ревизия отчёта. Разрешён только для готовой к приёмке версии.

При OK проверить неизменность реализации и выполнить свежую проверку Figma. При недоступном источнике или новой разнице не объявлять компонент актуальным. Это ограниченная защита от устаревших действий, не система совместного редактирования.

## Данные и правила

Реестр в Storybook-проекте: `source/figma/component-links.json`, с версией схемы. Запись содержит постоянный `componentId`, module path, стабильные story IDs, ссылку/идентичность Figma-файла, node IDs наборов/вариантов, явные темы, dependencies, источник актуальной базы, контракт и исключения.

Не связывать компоненты по отображаемому имени или порядку вариантов. Story IDs закрепить явно. Для Figma-файла сначала проверить доступность `fileKey`; Plugin API ограничивает его доступность. Если недоступен — ручная регистрация ссылки плюс проверяемый идентификатор корня документа и контрольные node IDs, проверенные на разных файлах и копиях. При неоднозначности сравнение блокировать. Не писать pluginData в готовые Figma-компоненты ради идентичности.

Удалённый/пересозданный node → «Связь требует уточнения», без автоматического переназначения по похожему имени. Новый вариант → структурное различие; требуется решение, входит ли он в контракт реализации.

Снимок содержит raw reads, нормализованные данные, SVG/asset hashes, definitions/property IDs, style/variable IDs, collections, modes, alias dependencies, версии схемы и нормализатора, warnings и полноту. Отдельно хранить хеш данных дизайна и хеш provenance, чтобы смена ID при неизменном цвете не выглядела как изменение цвета.

Нормализация:

- Учитывать размеры, layout/padding/gap, радиусы, paints/strokes/effects, opacity, типографику/сегменты текста, содержимое, структуру, варианты и props, bindings, темы, SVG.
- Игнорировать положение самостоятельного component set на рабочем листе и служебные timestamps; сохранять внутреннюю геометрию, порядок детей и порядок paint/effect-слоёв.
- Ключи объектов сортировать; массивы с визуальным смыслом не сортировать. Числовую погрешность вводить по полям после примеров, не единым округлением всей модели.
- `missing`, `mixed`, `zero`, `truncated`, недоступная библиотека и неразрешённый alias различать. Неполное сравнение не обновляет последнюю полную базу и не снимает маркеры.
- Исключения адресовать к конкретным компонентам/вариантам/полям; хранить причину и provenance. Новые согласованные дополнения не выдавать за Figma-источник.

Зависимости: обратный граф components → nested components/assets/styles/variables/aliases. Изменение Badge помечает MenuButton и Sidebar как затронутые. Отдельно показывать прямое отличие и влияние зависимости; не заявлять, что собственная геометрия Sidebar изменилась. Поддержать редактирование реестра зависимостей с проверкой неизвестных ссылок и циклов.

Хранение: исходные связи/контракты и воспроизводимые базы — в Storybook-проекте; временные отчёты и локальная приёмка — в `.figma-sync/`, исключённой из Git по умолчанию. Приёмка привязана к хешам исходников, токенов, ассетов и story-конфигурации; timestamp или один commit SHA не доказывает совпадение рабочего дерева. Переход на другую машину требует новой локальной приёмки до отдельного решения о переносе статусов.

## Этапы реализации и критерии готовности

### 1. Проверить два технических риска

Bridge: расширить handshake read-only сведениями для стабильной идентичности файла; сохранить совместимость существующего подключения. Проверить ограничения текущего manifest/API и source pinning.

Storybook: минимальный manager-addon для установленной версии 10.6.1 — панель и маркер через публичный `sidebar.renderLabel`, без вмешательства в DOM. Проверить Docs / Playground / Light / Dark, поиск и обновление маркера.

Готово: одинаковые имена двух файлов не путают источники; переподключение не теряет связь; тестовый статус виден возле нужного компонента без переименования story.

### 2. Реестр и начальная база одного компонента

Начать с Button: обе темы, актуальные raw exports, существующие контракты и исключения. Сопоставить raw → канонические токены → реализация; сомнительную базу оставить «Не настроено», не «Актуально». Существующую непроведённую визуальную приёмку не назначать автоматически.

Готово: один постоянный componentId объединяет все его stories и Figma-источники; база соответствует текущему коду и имеет записанное происхождение.

### 3. Сборщик снимка и diff

Добавить модули чтения/нормализации/diff в `src/bridge/sync/`, схемы в `src/shared/`. Использовать существующие чтения с закреплением файла на всю операцию. Дочитать ограниченные деревья и страницы переменных; лимит объёма завершает операцию статусом неполноты.

Готово: контролируемое изменение padding показывает старое → новое; перенос set на листе не создаёт шум; неполное чтение не даёт зелёный статус. Для проверки diff использовать фикстуры; готовую Figma не менять без отдельного согласования точных правок.

### 4. Локальный API и хранение

Добавить сервис в жизненный цикл `BridgeHost`, ограниченную авторизацию, валидацию запросов, timeout и атомарную запись состояния. Не менять семантику существующих MCP-методов и pairing.

Готово: addon выполняет compare без доступа к Figma pairing code; чужой Origin/проект отклоняются; disconnect сохраняет предыдущий результат с пометкой устаревания; перезапуск возвращает сохранённое состояние.

### 5. Интерфейс Storybook

Создать `.storybook/manager.tsx` и локальный addon. Маркер агрегируется на уровне компонента. Общая панель: компонент, статус, прямые изменения/зависимости, тема/вариант/поле, старое → новое, источник, время последнего полного сравнения. Действия: «Сравнить», открыть story/Figma, OK для готовой версии.

Статусы: «Не настроено», «Требуется перенос», «Готово к визуальной приёмке», «Принято»; ошибки/устаревание отображаются отдельно, поверх сохранённого состояния. Во время запроса показывать сравнение, не стирать прежний отчёт.

Готово: экспорт не снимает маркер; перенос меняет его смысл; только корректный пользовательский OK снимает его; устаревший OK отклоняется.

### 6. Стили, зависимости и остальные компоненты

Расширить на style tokens и variable modes; затем Checkbox, Toggle, IconButton, ResourceTag, Badge, MenuButton, Sidebar, TableRow. Порядок уточнить по фактическому графу. Учесть последующие экспорты Toggle/MenuButton/Sidebar, исключения ResourceTag и TableRow, derived-элементы между темами. Не выбирать «самый новый JSON» вместо цепочки обновлений генератора.

Готово: изменение общего токена отмечает всех реальных потребителей; Badge → MenuButton → Sidebar работает транзитивно; исключённые/derived варианты не создают вечную разницу; зависимости редактируются явно.

### 7. Проверка и поставка

Bridge: unit/integration для идентичности, нормализации, полноты, зависимостей, авторизации и переходов статуса; `npm.cmd run typecheck`, `npm.cmd test`, `npm.cmd run build`. Проверить regenerated `transfer/figma-codex-mcp-bridge`: все project skills присутствуют, pairing tokens, личные manifest/settings и node_modules отсутствуют.

Storybook: проверить manager-addon и последовательность сравнение → перенос → приёмка → OK; затем применимые typecheck/lint/build-storybook и браузерные проверки. Существующие запреты пользователя на проверки отдельных компонентов учитывать отдельно; не объявлять их отменёнными новым планом и не выдавать непроверенное за проверенное.

Негативные сценарии: неверный файл, потеря соединения, rename/delete, неполный экспорт, смена variable mode, отмена правки, новая правка перед OK, изменение кода после готовности к приёмке.

Готово: один сквозной сценарий проходит на Button, затем на цепочке Badge/MenuButton/Sidebar. Визуальную приёмку выполняет пользователь. Commit/push в рамках этого плана не разрешены автоматически.

## Рабочие решения и открытые вопросы

Для первой версии предлагаются: ручная кнопка как сигнал окончания серии правок; единый repo-side реестр; read-only Figma; исходная база из реализации; отдельная локальная приёмка; никакого автоэкспорта React-кода.

До расширения на все компоненты проверить на реальных данных: доступность идентичности файла; полноту remote styles/variables; сопоставление тем коллекций; правила значимости для спорных полей; происхождение каждой текущей базы. При отсутствии данных показывать ограничение и сохранять расхождение, а не угадывать.

Начинать с этапов 1–2. Полный перенос всех компонентов до проверки идентичности и manager API создаст лишнюю переделку.
