# Создание вариантов компонентов через MCP

Инструмент `create_component_variants` создаёт согласованные варианты. Первая версия проверена в живой Figma на двух светлых состояниях sort icon 24; результат в `sort-light-variants-2026-10-05.json`. Расширение размеров/новых значений проверено на sort icon 18: после согласованного переименования тёмных вариантов созданы три светлые копии, рамка увеличена до 75×103, исходная геометрия и defaultValue сохранены. Дерево, PaintStyle, SVG и повтор без дублей подтверждены; результат в `sort18-light-variants-2026-10-05.json`. Наличие сборки само по себе не означает, что запущенные мост и плагин уже перечитали её.

## Возможности

- Клонирование 1–20 локальных компонентов в их существующий локальный COMPONENT_SET.
- Явные сочетания существующих VARIANT-осей и координаты новых компонентов. Необязательный `newVariantValues`, например `{ "theme": ["light"] }`, разрешает новые значения только существующих осей; каждое объявленное значение должно быть новым и использовано в запросе.
- Необязательный `componentSetSize: {width,height}` меняет рамку набора через resizeWithoutConstraints, сохраняя геометрию исходных компонентов. Все старые и новые варианты должны помещаться в согласованную рамку.
- Назначение существующих PAINT-стилей fills/strokes по ID исходных слоёв; изменения применяются к новым копиям.
- Предварительный режим без записи, защита от изменения источника, повторов и конфликтующих сочетаний.
- Ответ с ID новых компонентов и sourceId→cloneId для всех клонированных слоёв.
- При ошибке удаление только созданных этой операцией корней. Если очистка не удалась, ошибка содержит полный `details.remainingNodeIds`.

Требуется layoutMode=NONE. Новые рамки не должны пересекать другие варианты. Без дополнительных параметров поддерживаются только существующие значения и исходные размеры. Новые оси не создаются; их согласованное переименование выполняется отдельно. Инструмент не импортирует библиотеки и не назначает новые переменные/режимы. Общий `update_node` по-прежнему не превращается в редактор VECTOR или компонентов.

Размеры и разрешённые значения входят в preview, expectedState и канонический запрос operationId. После записи проверяется нативная схема: допустимы только заявленные значения, прежние defaultValue и остальные определения сохраняются. При ошибке удаляются новые копии, затем восстанавливаются исходные размеры, если рамка по-прежнему соответствует размеру, записанному этой операцией. Ручное изменение рамки не перезаписывается: ROLLBACK_INCOMPLETE содержит componentSetSizeRestored=false и currentSize. Повтор проверяет также сохранённые размеры/схему; старые метки первой версии остаются совместимыми.

## Порядок вызовов

1. `list_connected_files` → активный файл → `get_file_overview`. Прочитать выбранный или явно указанный набор, его схему, исходные компоненты, слои и стили.
2. Вызвать `create_component_variants` с `dryRun: true` (значение по умолчанию), стабильным `operationId`, `componentSetId` и массивом `variants`.
3. Результат `status: preview` содержит канонические имена, назначения стилей, позиции и непрозрачную строку `expectedState`. Не изменять эту строку. Успешный preview не означает согласие пользователя или доказанную визуальную корректность.
4. Согласовать точный набор, источники, сочетания, позиции и стили. Если пользователь уже разрешил эти же изменения, повторное согласование не требуется.
5. Передать тот же запрос с `dryRun: false` и `expectedState` из preview. Изменившийся источник вызывает `SOURCE_CHANGED` до создания копий.
6. Результат `status: applied` содержит `variants[].nodeId`, `variants[].nodeMap`, фактическую схему. Прочитать новые узлы и SVG, сверить со согласованным изменением. Визуальную приёмку назначает пользователь.

Пример одного варианта:

```json
{
  "componentSetId": "1599:48606",
  "operationId": "sort-light-descending-v1",
  "dryRun": true,
  "variants": [{
    "sourceComponentId": "1599:48607",
    "properties": { "theme": "light", "state": "descending" },
    "position": { "x": 75, "y": 64 },
    "layerStyles": [
      { "sourceNodeId": "1599:48608", "strokeStyleId": "S:876da3bca148d8c8dbf5e060015b09c5a6b9fd9d," },
      { "sourceNodeId": "1599:48609", "strokeStyleId": "S:876da3bca148d8c8dbf5e060015b09c5a6b9fd9d," },
      { "sourceNodeId": "1599:48610", "strokeStyleId": "S:876da3bca148d8c8dbf5e060015b09c5a6b9fd9d," }
    ]
  }]
}
```

Эти ID относятся к прочитанному 5 октября файлу SD Enterprice. Перед применением перечитать реальный источник; пример не является разрешением писать в любой файл с такими ID.

## Повтор и ошибки

При TIMEOUT/Figma disconnect результат записи неизвестен. Не использовать новый operationId автоматически. Повторить прежний запрос с прежним operationId/expectedState либо прочитать набор. Если полный сохранённый результат найден и не изменён, команда вернёт `status: replayed` с прежними IDs даже после перезапуска плагина.

Служебные метки хранятся только на созданных компонентах. При удалении всех результатов или стирании всех меток восстановить историю операции невозможно; сначала инспектировать набор. Удаление части результатов вызывает OPERATION_RESULT_CHANGED, если сохранилась хотя бы одна метка.

`operationId` с другим запросом вызывает OPERATION_ID_CONFLICT. Занятое сочетание другого запроса вызывает VARIANT_ALREADY_EXISTS. Неисправная исходная схема — INVALID_VARIANT_SCHEMA. Чужой слой, пересечение или выход за границы — INVALID_ARGUMENT. Недоступный/неподходящий стиль — STYLE_NOT_FOUND/STYLE_TYPE_MISMATCH. Превышение 2000 узлов/16 уровней источника, 256 KiB снимка либо 90 KiB метки — LIMIT_EXCEEDED.

Очередь записи действует и в MCP, и в плагине. Файл фиксируется при вызове инструмента до ожидания очереди. Это не транзакция Figma: ручные изменения и потеря соединения возможны; отказ cleanup требует отдельного разбора оставшихся IDs. Исходные узлы автоматически не удаляются и не исправляются.

## Поставка

Изменения делать в исходном репозитории `E:/Codex/figma mcp plugin`. `npm.cmd run build` создаёт dist и заново формирует transfer/figma-codex-mcp-bridge. Не менять сгенерированные файлы вручную.

Обновить существующую регистрацию плагина через `npm.cmd run install:figma -- "<подтверждённая папка manifest>"`, сохраняя plugin ID. Затем перезапустить плагин Figma и клиент Codex/MCP, чтобы перечитались UI, код плагина и схема инструмента. Новая сборка на диске сама по себе не заменяет процессы, которые уже запущены. Второй сервер не нужен.

План и точный batch для двух светлых состояний: [план реализации](superpowers/plans/2026-10-05-create-component-variants.md).
